# Hive: agent guide

> Bash installer and controller for signed, digest-pinned suite releases, with upgrades, backups, restore rehearsals and the Hive Registry.

[Agent index](https://hivemagnus.com/llms.txt) · [Repository](https://github.com/ChefTaco/hive) · [Release 3.14.0](https://github.com/ChefTaco/hive/releases/tag/v3.14.0) · [Deployment overview](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/README.md)

## When to use Hive

Choose Hive to plan, install, upgrade and recover a tested combination of independent Hive:Magnus products. `hive.sh` verifies a signed release manifest, renders per-host Compose projects from digest-pinned images, and records what it did. Hive plans, applies and recovers; each product keeps its own data, credentials and recovery lifecycle. The controller needs only Bash, jq, OpenSSL and Docker Compose; no Node.js runtime.

| Profile | Adds |
| --- | --- |
| `core` | Oathweave, Emberpath, HiveMem, HiveSkills, HiveXUI, the HTTPS ingress and the Hive Registry, with their private Redis and Qdrant stores |
| `full` | Core plus Magnus, Cindertrace and ChatterMost, each with its own private PostgreSQL, and the optional Emberfold HTTP service |
| `custom` | Oathweave, HiveXUI, the ingress and the Hive Registry, plus the products you select |

Embermend is an explicit optional selection requiring compatible Magnus; see [its guide](https://hivemagnus.com/guides/embermend.md). No profile selects the Magnus web terminal gateway or [Ardent Project Studio](https://hivemagnus.com/guides/ardent-studio.md); every release offers the gateway, and interactive setup suggests Studio with the full profile. Selecting Magnus does not install a host agent: the guided setup offers one after installation, and `hive.sh magnus-agent install` installs it separately. [Ardent](https://hivemagnus.com/guides/ardent.md) is not a suite container: the Magnus host agent stages the Ardent package its signed dependency lock pins, and Magnus installs and manages it on the host; `hive.sh ardent setup` creates a first assistant profile through Magnus.

### What 3.8.0 changes for users

- **Oathweave 2.3.0, sign-in clients.** A confidential client must now send its client secret when it exchanges an authorization code; a public client must have started sign-in with a PKCE (S256) challenge. The suite's HiveXUI clients are public PKCE clients and need nothing. A confidential client that exchanged codes without its secret, such as Magnus's standalone UI registered as confidential, must be given it (`HIVE_OAUTH_CLIENT_SECRET` for Magnus), and a confidential client with no secret gets one with `POST /clients/{id}/rotate-secret`. Behind several proxy tiers, list every tier in `TRUSTED_PROXY_IPS`.
- **Emberpath 2.5.0, providers.** A stored provider credential stays with the server it was entered for: changing a provider's base URL to another scheme, host or port needs its secret again in the same change. Provider requests no longer follow redirects, so a provider behind a redirect fails until its base URL is the final address. Provider reads and configuration exports show `[redacted]` for credential header values.
- **HiveMem 1.7.0, workspaces.** Editing or moving a memory needs write access to its workspace, and to the destination when it moves; only an administrator can create the `default` workspace record; and another agent's profile summarises only memories you can read.
- **Magnus 2.10.0, per-node keys.** Each host agent gets its own node key while the shared node secret keeps working (`compat` mode). After the server upgrade, existing agents bind their key automatically for 30 days, and Magnus notifies you with each key's fingerprint. An agent that reaches Magnus through the suite's host agent port is the exception: it keeps the shared secret until you enroll it with a one-time token. `hive.sh magnus-agent install` enrolls a new agent with a token. HiveXUI shows the state under **Magnus > Fleet > Nodes**: a Node key column, a Node credentials panel with the fleet's progress towards enforcing keys, and a Node credential card on node detail, where administrators see the fingerprint and can revoke or reset a key. Enforcing keys only (`NODE_AUTH_MODE=enforce`) is opt-in; leave it off until every agent has a key. 2.10.0 and 2.10.1 agents with a key refuse the server's managed requests on enrolled nodes; Magnus 2.10.2, which 3.8.1 pins, fixes this and reaches those agents without upgrading them first, so upgrade the suite to 3.8.1 before the agents; see the [Magnus guide](https://hivemagnus.com/guides/magnus.md#per-node-keys). See [node keys](https://github.com/ChefTaco/hive/blob/v3.8.1/deployment/FULL.md#node-keys).

## Prerequisites

- A host running Ubuntu 22.04 or 24.04, or Debian 12 or 13, on amd64 or arm64, with sudo, 2 CPUs, 4 GB of memory and 20 GB of free disk. The `full` profile uses about 1 GB of memory when idle and about 6 GB of container images. On other Linux distributions, install Docker Engine with the Compose plugin and the tools `./scripts/install-prerequisites.sh --check` lists yourself.
- A DNS name for the browser address and a certificate and unencrypted key for it, from `tailscale cert`, your own CA or an ACME client.
- The signed services run as UID/GID 1000 (HiveXUI as 101), so run fresh setup as that account (usually the first account on the host) or with sudo.
- No model runtime: inference stays external.

## Install

The [installation guide](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/QUICKSTART.md) covers every step and setup question. On a fresh host:

```bash
git clone https://github.com/ChefTaco/hive.git && cd hive
./hive.sh --release latest
```

Expected result: the launcher resolves GitHub’s latest published, non-prerelease suite release once, prints its exact version, verifies it and starts guided setup. For a fresh local installation, setup offers to install Docker Engine and the required tools, using sudo only after showing its changes and asking for consent; the new `docker` group membership takes effect in a child shell, so no logout is needed. It then offers to create the installation directory. If Tailscale is already signed in with HTTPS Certificates enabled, setup suggests this host's HTTPS name and can obtain its certificate. Every offer can be declined.

To choose this release explicitly, as its release notes show:

```bash
git clone --branch v3.14.0 https://github.com/ChefTaco/hive.git hive && cd hive
./hive.sh --release 3.14.0
```

Failed lookups stop setup instead of falling back to an older release. An already-matching local checkout stays in use. Otherwise the launcher retains the tagged controller under `${XDG_DATA_HOME:-$HOME/.local/share}/hive/releases/` and prints its path. After setup, change to that retained checkout for the lifecycle and certificate commands below, and keep it while a renewal timer uses it. Return to the original launcher checkout when selecting a new release with `--release latest`.

The launcher checks the manifest signature against its original publisher key and verifies the signed controller source digest before executing it. It refuses changed release checkouts or a different key. For example, 3.14.0 verifies `releases/3.14.0.json` against its signature with `trust/publisher.pub`, then asks for the installation name, directory, host, browser address (the HTTPS origin), profile, bind address and certificate files (from 3.12.4, `tailscale` as the bind address selects the detected tailnet address, and a port in the HTTPS origin becomes the listener default), and, with Magnus, an optional port for host agents. It never asks for a password on the command line. It shows a plan, applies it after you confirm, and ends with the HTTPS origin, the initial sign-in file and the next commands. After installation it offers the certificate renewal timer and, when an agent port was selected, the Magnus host agent, full-node enrollment and then a first Ardent assistant. The steps that still need a person are recorded as a setup checklist: `./hive.sh status` and `./hive.sh setup` list the pending ones, `./hive.sh setup done ID` or `setup skip ID` settles one, and HiveXUI shows the list to administrators. If setup stops after writing its configuration, running it again offers to continue with that file.

### Manual host preparation

Existing configuration files, unattended commands and remote hosts keep explicit prerequisite and certificate management:

```bash
sudo ./scripts/install-prerequisites.sh --directory /opt/hive
# log out and back in for the docker group, then:
./scripts/install-prerequisites.sh --check
sudo ./scripts/console-certificate.sh tailscale
```

Expected result: `install-prerequisites.sh` shows its plan and asks before changing anything. It installs Docker Engine and the Compose plugin from Docker's apt repository after checking its signing key, plus jq, OpenSSL, curl, git, iproute2 and the other tools `hive.sh` uses, adds you to the `docker` group and creates `/opt/hive`; `--check` then prints `Ready`. `console-certificate.sh tailscale` writes `/etc/hive/tls/console.crt` and `console.key` for the host's MagicDNS name, owned by you. With your own certificate, check it instead with `./scripts/console-certificate.sh check --cert FILE --key FILE --name NAME`. Hive runs no ACME client itself.

To install from separately downloaded files instead, pass `--manifest`, `--signature` and `--trust-key`, still from the same tag's checkout. First check the key's fingerprint against the one in the [release notes](https://github.com/ChefTaco/hive/releases/tag/v3.14.0). The fingerprint is the SHA-256 of the DER public key:

```bash
openssl pkey -pubin -in trust/publisher.pub -outform DER | sha256sum
```

### Repeatable plans

For retries and for planning then applying, use the same exact release setup reported; do not resolve `latest` separately between the two steps. To prepare configuration separately or run unattended, supply the same installation JSON ([example](https://github.com/ChefTaco/hive/blob/v3.14.0/examples/installation.json), [schema](https://github.com/ChefTaco/hive/blob/v3.14.0/examples/installation.schema.json)). Interactive setup writes it to a protected configuration directory outside the checkout, by default `~/.config/hive/ID/installation.json`:

```bash
./hive.sh plan --config installation.json --release 3.14.0
./hive.sh install --config installation.json --release 3.14.0 --non-interactive --yes
./hive.sh status --config installation.json
./hive.sh doctor --config installation.json
```

Planning does not contact hosts. Per-product secrets, initial identities and internal transport keys are generated once into protected files, and retries check the exact inputs. Existing data, configuration, model resources and Compose projects are never silently adopted or overwritten. `./hive.sh --help` lists the lifecycle commands, including `init`, `upgrade`, `post-upgrade`, `setup`, `rollback`, `backup`, `backups`, `adopt`, `restore`, `rehearse`, `admin-access`, `ardent` and `migrate-native`. Commands other than `install`, `init` and `plan` find the installation file themselves when `~/.config/hive` holds exactly one.

For hosts beyond one, read the [distributed](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/DISTRIBUTED.md), [full](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md) and [custom](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/CUSTOM.md) guides.

## Sign in to HiveXUI

Visit the HTTPS origin you configured and sign in through Oathweave. [HiveXUI](https://hivemagnus.com/guides/hivexui.md) is the browser UI for every installed product, and shows sections only for products in this installation.

On a fresh installation, the initial username and password are in `config/initial-credentials.env` in the installation directory on the identity host, for example `/opt/hive/config/initial-credentials.env`; read them privately and leave the file in place. Add a passkey or authenticator app under **Oathweave > Account security**.

Keep the initial operator for recovery and work as your own administrator. Create it in **Oathweave > Users** with **IAM Administrator** as its initial role, then give it access to the installed products:

```bash
./hive.sh admin-access setup --release 3.14.0
```

Expected result: it lists the active administrators to choose from (`admin-access list` shows them), shows the products the account will administer, asks for sudo when needed, adds the Suite Administrator role, creates separate product accounts with reviewed grants, reconnects only the affected services and records `first-admin` and `administrator-product-access` as done in the setup checklist. Existing accounts and service identities are preserved; conflicting, locked or disabled accounts are refused. `admin-access setup NAME` selects an account by name, `--yes` confirms an unattended run after review, and `admin-access status NAME` reads the retained operation; after an interruption, repeat the same command. Sign out of HiveXUI and sign in with your own account, then take and rehearse a fresh backup. An external Magnus needs its own installation owner. See [administrator product access](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/QUICKSTART.md#administrator-product-access).

The installer copies the certificate into the ingress. After renewing it, run `./hive.sh tls-refresh --config FILE`; `sudo ./scripts/console-certificate.sh schedule --config FILE` does this weekly for a Tailscale certificate, and successful upgrades refresh an existing renewal service to the new checkout. Back up with `./hive.sh backup --config FILE --archive NAME --yes`, which keeps the suite serving; each application pauses only briefly, however much data it holds. See [backups](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/BACKUPS.md). Each upgrade keeps a backup and a restored rehearsal copy: on a single-host installation, `./hive.sh backups schedule enable --config FILE --at HH:MM` prunes old pairs every day with the [retention rules](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/BACKUPS.md#daily-pruning), and `./hive.sh backups schedule status --config FILE` shows the crontab line and the last run.

An installation migrated with `hive.sh migrate-native` keeps its accounts, roles and password hashes instead, and the owner sets a new administrator password once with a one-use reset token. Cutover writes the token to the configured `adminAccount.tokenFile` on the controller, mode 0600; it expires after 24 hours. On the host, run the installation's `bin/hive-set-admin-password` with `sudo`, or `hive.sh migrate-native set-admin-password --config FILE` from the controller. It prompts for the token and the new password without echo; neither can be a command-line argument. Then sign in and delete the token file. See [first sign-in](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/MIGRATE_NATIVE.md#first-sign-in).

## Upgrade

Return to the original launcher checkout. It selects and retains the new release controller; use an exact version instead of `latest` to review and apply a specific release. An upgrade shows its plan and requires confirmation:

```bash
./hive.sh upgrade --config installation.json --release latest
```

Some upgrades also need explicit migration approval with `--allow-migrations`:

- from 2.x, with existing PostgreSQL stores (Magnus, Cindertrace or ChatterMost);
- from a release before 3.4.0, when the installation includes Emberpath or HiveSkills, whose data formats changed;
- from a release before 3.6.0, when the installation includes Embermend;
- from a release before 3.8.0, when the installation runs Magnus, for Magnus 2.10.0's two additive migrations.
- from a release before 3.12.0, when HiveMem has data owned by `hive-router` (an installation migrated from the native Hive Router), which HiveMem 1.9.0's signed initialization moves to `emberpath` before re-linking the memory credential;
- from any release before 3.14.0, for every installation, because Emberpath 2.6.0 moves its router data from `emberpath-managed-format-2` to `emberpath-managed-format-3` (six nullable `Trace` columns and two indexes, additive and fast). Without the flag the upgrade stops before any service is stopped. The transition is declared from `managed-format-2` only, so an installation still on `emberpath-v1` (a release before 3.4.0) upgrades to a release from 3.4.0 to 3.13.5 first.

An upgrade from 3.7.x without Magnus, or with an external Magnus, needs none, and neither does one from 3.8.0 to 3.8.1 or from 3.8.1 to any later release up to 3.13.5 (for example 3.9.7 to 3.9.8, 3.10.0 to 3.11.0, 3.11.0 to 3.11.1, 3.11.1 to 3.11.2, 3.12.0 to 3.12.1 or 3.12.1 to 3.12.2, 3.12.2 to 3.12.3, 3.12.3 to 3.12.4, 3.12.4 to 3.12.5, 3.12.5 to 3.12.6, 3.12.6 to 3.12.7, 3.12.7 to 3.12.9, 3.12.9 to 3.13.0, 3.13.0 to 3.13.1, 3.13.1 to 3.13.2, 3.13.2 to 3.13.3, 3.13.3 to 3.13.4 or 3.13.4 to 3.13.5), except an upgrade to 3.12.0 or later where HiveMem has data owned by `hive-router`, as listed above. Magnus 3 upgrades from Magnus 2.10.2 only, so an installation that runs Magnus on a release before 3.8.1 upgrades to 3.8.1 first, then to 3.14.0. Before it changes anything, `hive.sh upgrade` checks a suite-managed Magnus as Magnus 3's start-up guard will and refuses, naming the blockers, while a node has no active key or its agent does not sign its evidence.

```bash
./hive.sh plan --config installation.json --release 3.14.0 --allow-migrations
./hive.sh upgrade --config installation.json --release 3.14.0 --allow-migrations
```

The installer takes a verified pre-change backup, rehearses the new runtime and migration on a disposable copy, then migrates the stopped live stores and rebuilds their indexes before activation. Credentials, ownership, PostgreSQL majors, application records and component selection are retained. HiveXUI is unavailable while services and stores are stopped or migrated; the duration depends on the data and index rebuilds. A core installation has no PostgreSQL store to migrate, and moving between releases with unchanged datastore formats does not repeat a migration.

**Code-only rollback across the 3.0.0 PostgreSQL boundary is refused.** `./hive.sh rollback` can still return to a compatible storage format, but recovery from the PostgreSQL collation change requires the verified original-state backup, rehearsed with the retained original controller and images, and reconciliation of later writes; it must not discard them. A failed or uncertain live migration holds the transaction for recovery: repeat exactly the same command rather than editing transaction or runtime receipts. Read the release notes, [advisory remediation](https://github.com/ChefTaco/hive/blob/v3.14.0/docs/ADVISORY_REMEDIATION.md#postgresql-needs-a-separate-migration-proof), the [upgrade procedure](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/QUICKSTART.md#8-upgrade) and [UPGRADING](https://github.com/ChefTaco/hive/blob/v3.14.0/UPGRADING.md) first.

From 3.12.3, every container the controller creates rotates its Docker log (`json-file`, 10 MB per file, 3 files). The setting is part of the rendered Compose file, so the first upgrade to 3.12.3 recreates every container on each host, datastores and unchanged images included. Data is kept, but the log of each replaced container is removed with it: save what you need first, for example with `docker compose -f INSTALL_DIR/compose.json logs --no-color`. To use other bounds, set `containerLogs` (for example `{"maxSize":"50m","maxFiles":5}`) in the installation file before the upgrade. Controllers before 3.12.3 refuse that key, so remove it before rolling back to 3.12.2. See [Suite 3.12.3](https://github.com/ChefTaco/hive/blob/v3.14.0/UPGRADING.md#suite-3123-bounded-container-logs-and-security-updates).

From 3.13.0, HiveXUI's **Installed software** page reads the Hive Registry's inventory with the browser client `hivexui-registry`, which an existing installation gets in two steps. Before any `plan`, `rehearse` or `upgrade` from 3.12.x to 3.13.0 or later, merge `"hivexui-registry":{"audience":"hive-registry","permissions":["registry:inventory"]}` into the JSON of `IAM_BROWSER_CLIENT_POLICIES` in `config/oathweave.env`, keeping every existing key, so the upgrade starts Oathweave with it. A rehearsal or upgrade pins the deployment inputs of its plan, so an edit after one of them makes that plan refuse ("Deployment input artifacts changed for this plan") until the installation has a new `configurationRevision`. After the upgrade, run `./hive.sh console-clients add` (or `./hive.sh post-upgrade` where it runs it), sign out of HiveXUI and in again, and run `./hive.sh status` once so the registry records what the hosts run. Without the policy, `console-clients add` skips the registry client and names it; the other clients are unaffected. A rollback to 3.12.9 keeps the new registry files, which that registry ignores, but stops with the same message until you set a new `configurationRevision` in `installation.json` and run it from the retained 3.12.9 checkout. See [Hive Registry inventory](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#hive-registry-inventory) and [Suite 3.13.0](https://github.com/ChefTaco/hive/blob/v3.14.0/UPGRADING.md#suite-3130-hive-registry-141-and-the-installed-software-view).

From 3.14.0, the upgrade's pre-change backup is also the way back. The installer runs `emberpath migrate` on the restored copy, then once on the stopped live store, and a code-only `rollback` from 3.14.0 is refused because no earlier release reads `emberpath-managed-format-3`; recover with the verified pre-upgrade backup. Ardent Project Studio 0.5.1 runs its migrations 7 to 10 on its first start: they are additive and keep existing rows, but Studio 0.4.x no longer starts on a database they have run on, so keep the backup until you have checked Studio on 0.5.1. A fresh Studio gets `ARDENT_STUDIO_INSTANCE_ID` set to the installation ID, so its execution references name the installation; an existing Studio keeps `local`, and to change that, add the line to `config/ardentstudio.env` before you run `plan`. Ardent 3.2.0 resumes interrupted tasks after a restart by default (`execution.recovery.enabled: false` in the profile's Ardent configuration restores the earlier behaviour). Release any extension package that pins an exact `@hivemagnus/ardent` peer for 3.2.0 before Magnus moves the agents, because a managed upgrade holds the runtime when a peer differs; until a profile moves to Ardent 3.2.0, its recovery, lineage and artifact reads answer `409 unsupported_capability`. Magnus 3.3.0 adds no migration and the optional settings `MAGNUS_HIVE_REGISTRY_URL` and `MAGNUS_HIVE_REGISTRY_TOKEN_FILE`, which the suite does not set and you do not need. See [Suite 3.14.0](https://github.com/ChefTaco/hive/blob/v3.14.0/UPGRADING.md#suite-3140-ardent-execution-recovery-lineage-and-artifact-transfer-v2).

After upgrading, switch to the retained checkout the launcher printed and finish the remaining steps. `post-upgrade` shows and confirms each change: it updates Magnus host agents older than the release (unattended, only with `--yes`), adds missing HiveXUI browser clients to Oathweave, marks the setup checklist items it completes as done, and lists what is left. A successful interactive upgrade also offers `admin-access setup`; after an unattended one, run it when ready:

```bash
./hive.sh post-upgrade --config installation.json --release 3.14.0
./hive.sh magnus-agent install --config installation.json --release 3.14.0
```

`magnus-agent install` is the same scope-preserving package maintenance path run on its own: it upgrades the agent and stages the verified Ardent package while keeping its enrollment scope, node identity, profiles and completed history; from 3.13.5, on the Magnus host it also records the `magnus-agent-enrolled` checklist item once the pinned agent runs and Magnus has accepted its heartbeat. Full-node enrollment remains a separate explicit operation. An updated agent is not re-enrolled for a node key either: with Magnus 2.10 it binds its own key automatically, and with Magnus 3 an agent that has a key keeps it while one without a key is enrolled with a one-time token. Agents that Magnus manages cross from 2.10.2 to 3.x by way of 2.10.3, with `magnus-server agents upgrade --to 2.10.3` and then `--to 3.3.0 --allow-major` (or **Allow major upgrade** in HiveXUI), and move from an earlier 3.x with `--to 3.3.0` within the major, each after a `--dry-run`; see the [Magnus guide](https://hivemagnus.com/guides/magnus.md#upgrade-to-301). Then, in **Magnus > Ardent > Installations** in HiveXUI, stop running profiles, choose **Update package** and start them again. From 3.9.1 `./hive.sh post-upgrade` asks Magnus, read only, which installations are behind the Ardent version their node agent stages, names them, and records `ardent-packages-updated` as done once none is; with an external Magnus it asks through Ardent Project Studio's service identity, so without Studio record it with `./hive.sh setup done ardent-packages-updated`.

## Fleet hosts and security events

With Magnus and a port for host agents, one command installs the Magnus agent on the Magnus host, or with `--host` on another fleet host, and waits for Magnus to accept its first heartbeat. Without a suitable Node.js it offers to install Node.js 24 from NodeSource's signed apt repository (`--install-node` agrees unattended). It installs exactly the agent version the release pins, after checking the package's integrity, never prints the node credentials, and stages the pinned Ardent package without installing or starting a runtime. With Magnus 2.10 it gives a new agent its own node key through a one-time enrollment token that is never printed or passed on a command line (with Magnus 3, every agent without a key, and it copies no fleet-wide node secret to agents), and ends with the key fingerprint to compare with Magnus's notification; `magnus-agent status` includes the node key state. On an installer-owned single host, `magnus-agent enroll` then reviews and enables full node capabilities: commands, managed cron and a selected restricted web terminal. A fresh Cindertrace ingests nothing until a collector exists; `cindertrace-collector add` generates a collector's credential into an owner-only file on the Cindertrace host and never prints it.

```bash
./hive.sh magnus-agent install --config installation.json
./hive.sh magnus-agent enroll --config installation.json
./hive.sh magnus-agent status --config installation.json
./hive.sh cindertrace-collector add edge --sources tailscale --config installation.json
./hive.sh cindertrace-collector list --config installation.json
```

With Magnus, HiveMem and Oathweave and an enrolled host agent, `ardent setup` installs the staged Ardent package and creates the `assistant` profile through Magnus's **New Agent** workflow. It asks for an OpenAI-compatible model API URL (including `/v1`) and the model name, configures HiveMem, starts the profile and makes a real model request before reporting success. It accepts only model endpoints that need no separate API key. Existing profiles are preserved, and repeating it follows its retained operation instead of creating another profile; a failed operation is resumed only explicitly, after review. Magnus-created profiles are included in native suite backups, so do not add them to the installation file's `agents`. From 3.14.0, setup waits up to 60 seconds for Magnus to release the install command's node owner before it creates the profile, and a create refused before any request was sent drops its receipt and says so, so `./hive.sh ardent setup` can simply run again; an ambiguous refusal still keeps the receipt and repeats nothing.

```bash
./hive.sh ardent setup --config installation.json
./hive.sh ardent status --profile assistant --config installation.json
./hive.sh ardent check --profile assistant --config installation.json
```

From 3.14.0, `doctor` and `ardent status` also list the [agent dependencies](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#agent-dependencies) Magnus resolved for Ardent (`GET /api/v1/ardent/dependencies`, Magnus 3.3.0 or later): HiveMem, HiveSkills and Emberpath, each with its status (`usable`, `missing`, `unsupported` or `awaiting_configuration`), its source (`override`, `registry` or `none`) and, when it is not usable, why; `ardent status` adds the report to its JSON as `dependencies`. A Magnus before 3.3.0 prints `Magnus is too old to report agent dependencies (needs 3.3.0)`, and neither command fails because of the report. The suite configures HiveMem and HiveSkills for Magnus explicitly (`source: override`) and does not set Magnus's Registry discovery, so Emberpath reports `missing` unless `MAGNUS_ARDENT_EMBERPATH_URL` names an address the fleet hosts' agents can reach. A resolved dependency is only available: HiveMem enrollment, skill installation and channel enablement keep their own steps and credentials.

See the [setup checklist](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#setup-checklist), [creating an Ardent assistant](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#create-an-ardent-assistant), [Magnus host agents](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#magnus-host-agents), [Ardent Project Studio](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#ardent-project-studio), [sending security events](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#sending-security-events-to-cindertrace), [events from a separate logging host](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#events-from-a-separate-logging-host) and [adding a product to an existing installation](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/FULL.md#adding-a-product-to-an-existing-installation).

## Hive Registry

Every installation runs a Hive Registry: its install catalog and lookup API, a small SQLite container on the host serving HiveXUI. It is mandatory, one per installation, and unrelated to [HiveSkills](https://hivemagnus.com/guides/hiveskills.md), the skills registry. It holds the products the signed release offers, what this installation actually runs, the links an operator or client needs, the setup checklist, each product's announced capabilities such as its event feed, and an append-only history. It has no HiveXUI section of its own; HiveXUI reads it to decide which sections to show and for its Setup page.

```bash
./hive.sh registry list --config installation.json
./hive.sh registry get emberpath --config installation.json
```

`list` also has `installed`, `summary` and `history` forms. `hive.sh` is the normal writer; `registry add`, `update` and `remove` cover externally managed products only, and any credential in an entry is refused. The ingress passes only explicit `GET` routes under `/api/registry/`, so writes never leave the private network. `status` reports drift by name and `doctor` fails on any drift. See the [API reference](https://github.com/ChefTaco/hive/blob/v3.14.0/docs/hive-registry-api.md).

From 3.13.0 (Hive Registry 1.4.1), the registry also serves administrators an [inventory](https://github.com/ChefTaco/hive/blob/v3.14.0/docs/hive-registry-api.md#inventory), `GET /v1/inventory`, announced with the `inventory.v1` capability: each product's signed release pin (version and image digest) beside what each host reports it runs (the configured and local image, whether they match, state and health). HiveXUI's **Installed software** page shows it. It accepts the shared credentials, or an Oathweave token for the `hive-registry` audience with `registry:inventory`, which `SUITE_ADMIN` holds through the `hivexui-registry` client; every other route refuses such a token. `hive.sh status`, `doctor` and completed `install`, `upgrade`, `rollback` and `adopt` commands record what they observe (`PUT /v1/observations`), best effort, so the page shows the state as of the last of them. The inventory carries no origin, internal endpoint or credential, and the storage format is unchanged.

From 3.14.0 (Hive Registry 1.5.0, image 2.0.13), a product's connection read with a credential (`GET /v1/products/{id}/connection`) also carries [service capabilities](https://github.com/ChefTaco/hive/blob/v3.14.0/docs/hive-registry-api.md#service-capabilities), `serviceCapabilities`, beside `internalEndpoints`: what the product offers other products, each with the first version offering it. The suite catalog declares Emberpath `emberpath.execution-trace.v1` and `retry-signal.v1` (2.6.0), HiveMem `memory.v1` (1.9.1), HiveSkills `skills.pinned-release.v1` (1.9.0) and Magnus `ardent.recovery.v1`, `ardent.lineage.v1` and `artifact-transfer.v2` (3.3.0), and `hive.sh` records them with each connection. An entry is `confirmed: true` only once the product is recorded as running that version; while it is still activating, or when the registry cannot tell the version (an external Magnus), it is `confirmed: false`, and the reader compares `since` with the version the product reports. `?capability=NAME` narrows a connection to that entry (`404 capability_not_offered` otherwise), and `GET /v1/products?capability=NAME` lists the products offering it. A capability makes an endpoint available and never grants a permission. The public views and the browser contract are unchanged.

## External inference

Ollama, llama.cpp, other inference services and hosted APIs are external dependencies. Hive only verifies connectivity, model discovery, generation and streaming, then registers verified providers with Emberpath. It never installs or manages inference services, model downloads, storage, licenses or GPUs. See [external inference](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/INFERENCE.md).

## Existing installations

A native installation, with Router, IAM, HiveMem and, where installed, Skills running as systemd services, moves onto the suite on the same host and ports with `hive.sh migrate-native`. It keeps every native port, certificate, issuer, key and account. Read [migrating a native installation](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/MIGRATE_NATIVE.md) before any separately approved maintenance window. `adopt` takes over existing Compose stacks only.

The npm launcher `@hivemagnus/hive` and the other 1.x npm packages are the legacy line. The suite products supersede them; 1.2.2 was the final legacy npm release and its archived source remains at that tag. Installations the launcher manages follow [UPGRADING](https://github.com/ChefTaco/hive/blob/v3.14.0/UPGRADING.md). To bring one under the controller, rehearse its own backups and read [existing-data rehearsals](https://github.com/ChefTaco/hive/blob/v3.14.0/deployment/EXISTING_DATA_REHEARSALS.md) first. Preserve each installation's state.
