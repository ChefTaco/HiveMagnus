# HiveXUI

> The single browser UI for a Hive installation: fleet, identity, models, memory, skills, security, chat and team projects in one shell, with sections only for installed products.

[Agent index](https://hivemagnus.com/llms.txt) · [Repository](https://github.com/ChefTaco/HiveXUI) · [Release 0.15.0](https://github.com/ChefTaco/HiveXUI/releases/tag/v0.15.0) · [Theme](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/docs/THEME.md)

## Responsibility

HiveXUI is a static TypeScript and React application. The container serves compiled assets only: no application backend, database access, signing keys or infrastructure credentials. Same-origin HTTPS ingress forwards the signed-in user's own credentials to the owning API. Access tokens stay in memory; Oathweave owns the SSO session. Nothing puts credentials in URLs or browser storage.

HiveXUI shows one section per installed product, plus Hive and System. The Hive Registry is the source of which products are installed when it is reachable; a section shows only for a product that the runtime `products` configure and the Registry lists. If the Registry is unreachable or unreadable, HiveXUI follows `runtime.json` and warns on the overview. A bookmark to an absent product opens the overview. `Ctrl` or `Cmd` + `K` searches every visible screen and, from 0.7.0, records in the installed products you can read, such as Magnus nodes, Studio projects, memories, cases, skills and users. There is one theme for now: dark, in the Magnus look. From 0.13.0 it follows `prefers-contrast: more` (brighter secondary text and outlines, no glow or backdrop) and forced colors.

The [HiveXUI README](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/README.md) retires the products' own web UIs, except Magnus's standalone console for installations without the suite. It kept Cindertrace's console only until Cindertrace shipped HiveXUI in local mode for standalone installs and the lab, which [Cindertrace 0.8.0](https://hivemagnus.com/guides/cindertrace.md) does: it removes its console, and HiveXUI is its only UI. Every product API stays usable on its own, by native clients and scripts. Do not treat synthetic screenshots as evidence of backend authorization or workflow parity.

From 0.10.0, HiveXUI signs in to Cindertrace without Oathweave in two cases, and then shows only Cindertrace's pages and refuses requests to products the runtime does not configure. In **local mode**, for a standalone Cindertrace or its investigation lab, `runtime.json` names only Cindertrace and no `identity` (`{"schema": 1, "mode": "local", "products": {"cindertrace": "/api/cindertrace"}}`) and HiveXUI uses Cindertrace's own API sign-in. On a suite installation with Cindertrace, the sign-in page offers **Oathweave unavailable? Cindertrace recovery sign-in** with Cindertrace's local administrator; the choice lasts for the tab. From 0.13.0, a Cindertrace local account that requires TOTP (Cindertrace 0.10.0) is asked for its authenticator code on both. See [Cindertrace sign-in](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/README.md#cindertrace-sign-in-local-mode-and-recovery).

## Sign-in and re-authentication

From 0.14.0, HiveXUI signs in only through Oathweave's own sign-in page (or, in local mode, Cindertrace's own store), and no product receives a person's password. The Emberpath password sign-in (`/api/auth/login`), its multi-factor retry and the password re-authentication (`/api/auth/reauthenticate`) are removed, with the legacy upgrade panel that used them; upgrades run on the installation controller. A `mode: "legacy"` runtime, which used to sign in with a password through Emberpath, now shows **Configure Oathweave browser sign-in** instead of a sign-in form: add the `identity` block (the installation's `IAM_BROWSER_ISSUER`, its Oathweave API prefix and a public client per product) and reload. Cindertrace's local mode and recovery sign-in are unchanged. See [re-authentication](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/README.md#re-authentication-step-up) and the [sign-in portal](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/README.md#sign-in-portal).

- **Sign in with a passkey**, on the sign-in form and the `/auth/authorize` portal, uses Oathweave's passwordless sign-in: a discoverable passkey with user verification, no password, so passkey-only accounts can sign in. It shows when the browser supports WebAuthn, never on Cindertrace's local sign-in, and disappears with a notice when Oathweave answers 404 (`IAM_PASSWORDLESS_PASSKEYS=false`).
- **Re-authentication.** A product that needs a recent sign-in before a sensitive action answers `403 STEP_UP_REQUIRED`. HiveXUI then makes an OpenID Connect round trip in the page, so the pending action stays in memory: for Emberpath it takes a single-use nonce from `POST /api/emberpath/auth/step-up/challenge`, asks Oathweave to authorize the product's public client with `prompt=login`, S256 PKCE and the nonce, and gets `LOGIN_REQUIRED` with a login ticket. **Verify your identity** offers **Verify with a passkey** (a user-verified passkey alone) and **Password and passkey** (the password with the authenticator code or a passkey); either goes only to Oathweave's step-up endpoint, for the same session and user. HiveXUI repeats the authorization with the ticket, checks the ID token (signature, issuer, client, nonce, the same `sub`, an `auth_time` no older than the start, `at_hash`), sends it to `POST /api/emberpath/auth/step-up` for Emberpath, and renews every product's access token. A refused read is repeated once; a refused change is not replayed, and the page says to submit it again. Cancelling leaves the action undone and shows `REAUTH_CANCELLED` in a dismissible notice.
- **The sign-in portal** honours `prompt` (`login`, `select_account`, `consent`, `none`) and `max_age`, repeats a forced sign-in with Oathweave's login ticket, and returns **Cancel**, a declined consent and `prompt=none` errors to the application's exact callback.

0.14.0 needs Oathweave 2.7.0 or later for re-authentication and passkey sign-in, and uses Emberpath 2.10.0's step-up; against an older Emberpath the step-up challenge answers 404 and the renewed token carries the new `auth_time`, which that Emberpath checks. These three releases arrived together in Hive 3.15.1; see the [Oathweave](https://hivemagnus.com/guides/oathweave.md#browser-sign-in-and-re-authentication) and [Emberpath](https://hivemagnus.com/guides/emberpath.md#signing-in-and-re-authentication) guides. From 0.15.0, with a drawer or dialog open, the outcome of a step-up (verified or cancelled) is shown inside it, beside its actions, in a polite live region with **Dismiss notice**, instead of a toast over its primary action, and focus returns to the action that asked; other toasts move beside an open drawer. With Emberpath 2.11.0 (Hive 3.15.2), opening API Keys, Clients or Roles with an older sign-in no longer asks you to verify your identity; issuing or changing a key still does.

## In a Hive installation

[Hive](https://hivemagnus.com/guides/hive.md) {{hm.suite}} installs HiveXUI {{hm.version:hivexui}} (pinned since {{hm.since:hivexui}}), a digest-pinned image, next to the ingress, in every profile, and writes its public runtime file. There is nothing else to configure. HiveXUI is the suite's browser UI: Emberpath, HiveSkills and, from Cindertrace 0.8.0, Cindertrace no longer bundle a web UI of their own. Every product's errors show a consistent message with the product's code and request ID, and destructive actions are confirmed in one shared dialog.

From 0.8.0, with Magnus 2.10, **Magnus > Fleet > Nodes** shows each host agent's node key: a Node key column in the list, a Node credentials panel (administrators and operators) with the mode, the automatic binding window and what still blocks enforcing keys, and a Node credential card on node detail. Administrators see key fingerprints there, approve or reject a binding Magnus refused for its address, and revoke or reset a key behind the shared confirmation; issuing an enrollment token and rotating a key stay command-line and API steps. Against a Magnus without per-node credentials all of this stays hidden. On **Emberpath > Providers**, changing a provider's base URL to another server asks for its secret again before saving, matching Emberpath 2.5.0.

From 0.9.0, with Magnus 3, the Node credentials panel says whether the node-auth mode is set on the server or is the default (enforce), warns about a deprecated explicit `compat` or `warn`, names agents that still need an upgrade, and shows the server key rotation: the active and staged key fingerprints, how many agents pin each, and the next step, which stays a command-line and API step. In enforce mode Reset on node detail stays disabled and says why; Revoke still works. Against a Magnus before 3.0.0 the panel reads as in 0.8.0.

From 0.9.1, against a Magnus that reports 3.0.1 or later, **Magnus > Fleet > Upgrade agents** offers ADMIN an **Allow major upgrade** option, the browser counterpart of `magnus-server agents upgrade --allow-major`. Turning it on asks first and explains the stepping stone (2.10.x to 2.10.3, then 3.x) and the one-hour major-upgrade authorization the server signs for each node with its server key, which the agent verifies against the key it pins, so the node needs a bound node key. The drawer then checks eligibility with the option, says in the run confirmation how many selected agents cross a major, lists the agents held back with Magnus's cause and remedy (`MAJOR_NEEDS_STEPPING_STONE`, `MAJOR_NEEDS_NODE_KEY`), and marks the rollout "major upgrades allowed". The option resets each time the drawer opens. Against a Magnus before 3.0.1 the drawer keeps its manual major-version notice and offers no option; operators and viewers read that an ADMIN can include those agents.

From 0.9.2, with Magnus 3.1.0, the Software revisions card on node detail reads the node's read-only software status (`GET /api/v1/nodes/:nodeId/software`) when you press **Check versions** or **Read update cache**: installed versions, and the pending updates in the node's existing APT cache with its refresh time. It dispatches no command and runs nothing on the node, and node viewers can use it; **APT upgrade** stays an explicit operator command. Against a node agent older than 3.1.0 (`SOFTWARE_STATUS_UNAVAILABLE`) or a Magnus server without the route, the card says the status is unavailable and to update Magnus and the node agent, and never falls back to a shell command.

From 0.13.0, a request without its own deadline fails after 30 seconds for a read or 120 seconds for a write and names its request ID. A 401 from any product asks Oathweave whether the browser session still exists, and signs out only if it does not; an identity outage keeps you signed in. Signing out in one tab signs out every tab and always ends the ChatterMost cookie session. The sign-in form has no prefilled username. A tab left open across an upgrade offers **Reload** from `/version.json`, which the image serves with `Cache-Control: no-store`; a proxy in front of the UI must not cache it either. Newer views need newer products and stay hidden or show the product's refusal against older ones: Studio **Members** and **Purge** (Ardent Project Studio 0.7.0), the Skills **Registry release** panel (HiveSkills 1.10.0), Embermend **Accepted risk** and **Assessment profiles** (Embermend 0.5.0) and Emberpath **Adaptive** routing.

## Emberpath keys for agents

From 0.15.0, with Magnus 3.5.0 or later, HiveXUI delivers the Emberpath client key that an Ardent agent with an Emberpath model alias needs; the key goes to Magnus once and is never filled or remembered by the browser or shown again.

- **New Agent.** With an Emberpath alias, the Model step has a required **Emberpath client key** password field, with help on issuing one and an **Issue a key in Emberpath** link that opens Emberpath's Issue key drawer, named for the agent, in a new tab. The key is sent as `emberpath_client_key` and dropped from the page as soon as the request leaves. Magnus's refusals show beside the field they concern: `EMBERPATH_KEY_REQUIRED`, `EMBERPATH_KEY_INVALID` and `EMBERPATH_KEY_FORBIDDEN` on the key, `EMBERPATH_ALIAS_UNAVAILABLE` on the alias, and `EMBERPATH_NOT_EXPLICIT` as a server setting to fix. When **Resume** answers `EMBERPATH_KEY_REQUIRED` because the server no longer holds the key, the wizard asks again and **Resume with key** sends it.
- **Set Emberpath key** on an Ardent profile's page (Magnus ADMIN, llama.cpp backend) sets or rotates the key of an existing agent through Magnus's `POST /ardent/installations/:nodeId/profiles/:name/model-credential`, then follows the operation (check, deliver the key, restart, wait for the agent). Use it for alias agents created before Hive 3.15.2, whose model requests Emberpath refused with 401.
- **Create agent from definition** in Studio. An agent template's page in the Gallery has **Create agent**: choose the node and profile ID, bind the Emberpath alias when the definition names none, and give the key when the definition's model is an alias. Magnus's preflight runs first (`deploy-check`), then the install (`deploy`), and the operation is followed until the agent runs; `SECRET_UNBOUND`, `EMBERPATH_KEY_*` and `PREFLIGHT_FAILED` show on the key, `MISSING_BINDING` and `EMBERPATH_ALIAS_UNAVAILABLE` on the alias.

Against Magnus 3.4.1 or earlier, New Agent with an alias answers `400 VALIDATION_ERROR` and Set Emberpath key `404`; Create agent from definition with an alias also needs Ardent Project Studio 0.8.0, and 0.7.0 refuses the key with `400 VALIDATION_ERROR`. Upgrade Magnus, then Studio, then HiveXUI; agents with a model URL and codex definitions are unaffected. 0.15.0 has no migration and no `runtime.json` change, and a downgrade to 0.14.0 is safe. See [Studio](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/docs/STUDIO.md) and the [changelog](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/CHANGELOG.md).

## Installed software

From 0.11.0, **Installed software** (`/?page=software`, linked from the Installation overview for administrators) puts the signed release's pins beside what the hosts report: each host's activation receipt against the release version and manifest digest, and each component's pinned version and image digest against the image digest, state and health its host last reported, which `hive.sh` records in the Hive Registry. A digest that differs from the pin is flagged whatever the version label says. For Magnus, the page reads Magnus's installation report (`GET /api/magnus/system/installation`, Magnus 3.2.0 or later, for Magnus administrators): the running version against the pin, whether it is a native npm install, and every dependency npm resolved differently from the `npm-shrinkwrap.json` the Magnus package shipped. Host agents are counted against the pinned version; they report no installed integrity yet. Against a Magnus without the report the Magnus panel says so and the rest of the page still shows.

The inventory is the registry's only signed-in read, with the fixed Oathweave client `hivexui-registry` and prefix `/api/registry`, so `runtime.json` does not change. HiveXUI enables it when the registry's public product entry announces `inventory.v1` (Hive Registry 1.4.0 or later); otherwise the page says to upgrade and run `./hive.sh console-clients add`, which is also how an upgraded installation adds the client. See [Installed software](https://github.com/ChefTaco/HiveXUI/blob/v0.15.0/README.md#installed-software) and the [Hive guide](https://hivemagnus.com/guides/hive.md#upgrade).

## Execution recovery, lineage and delivery

From 0.12.0, HiveXUI shows the execution recovery, lineage and artifact transfer of Ardent 3.2.0, Magnus 3.3.0, Ardent Project Studio 0.5 and Emberpath 2.6.0. Against older products these views stay hidden or say what is missing, and Studio fields added in 0.5.0 are read as optional.

- **Studio room.** Interrupted tasks carry a state chip: **Recovering** (Ardent continues the run under the same task), **Needs decision (effect unknown)** (held, and counted among the blockers) or **Unknown outcome** (cannot be resumed). A held task has a recovery panel with the reason and only the decisions the backend lists, each confirmed with what it does to the interrupted call and sent once with an idempotency key. The lineage drawer traces a task from the originating request through hand-offs, reassignments and workflow steps to each Ardent attempt's model attempts, linked to their Emberpath traces, tool calls and artifacts. The **Workflows** drawer shows branch-and-join runs with their steps, needs, waiting and blocked reasons and the node actions Studio offers (retry, skip, cancel run).
- **Deliverable Review.** Preview renditions are shown inline; **Download original** streams with progress, resumes with `Range` up to five times after a dropped connection and saves only after the SHA-256 matches. The Receiving strip shows import progress, resumes and failures, and a Provenance panel links to the execution history.
- **Agent 360.** The Executions tab lists the profile's recent Ardent tasks with state, recovery, root and parent, linked to the Magnus task view; Traffic gains an execution column and a **Linked to executions** view, and its outcome badge reads Emberpath's outcomes correctly (every trace showed as failed before).
- **Magnus.** The Ardent overview shows the agent dependency report (`GET /ardent/dependencies`): HiveMem, HiveSkills and Emberpath as usable, missing, unsupported or awaiting configuration, with where each was found, and **Check again**. The Ardent profile page lists every artifact the agent registered and, when the profile offers artifact transfer v2, downloads through `/content` with the real type and file name, checking the digest before saving.

## Build it

```bash
npm ci --ignore-scripts
npm run build
npm test
```

Expected result: compiled assets in `dist/`. `Dockerfile` serves them as UID 101. Without Hive, mount a public `runtime.json` listing product prefixes and Oathweave public clients, or the local-mode file above for a standalone Cindertrace, and configure HTTPS and API routing in a separate ingress, as the README describes. Runtime JSON contains public identifiers only.
